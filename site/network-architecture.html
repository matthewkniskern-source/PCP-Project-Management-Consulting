Protected access by design.

Proposed cloud-first, identity-centered network model

LOGICAL TOPOLOGY

Future-state network architecture

The PCP modernization plan separates the public informational website from employee applications and protected records. Staff access follows verified identity, device posture, least-privilege authorization, and application-specific policies rather than trusting a user simply for being on a company network.

Segmentation and security controls

Identity and endpoint trust

Enroll company-managed devices in endpoint management, require MFA, use Conditional Access for sign-in risk and device compliance, and disable stale accounts promptly. Third-party consultants receive time-bounded access aligned to assignments.

Application and data isolation

Enforce authorization on the server, separate public hosting from internal application services, restrict databases to private networking, encrypt transport and storage, and maintain tested backups and retention controls.

Monitoring and resilience

Centralize identity, endpoint, application and infrastructure events. Log administrative sign-ins, PIM role activations, privileged sessions where supported, and sensitive configuration changes; review alerts and anomalies. Maintain break-glass access, recovery ownership, access reviews, and tested restoration procedures.

Privileged access

Separate daily-use and administrative identities, require dedicated hardened privileged-access workstations (PAWs), and use Entra Privileged Identity Management (PIM) for eligible, time-bound role activation. Match cloud RBAC and operating-system rights to the task. Azure Bastion remains optional for private Azure VM sessions; SaaS and PaaS management does not ordinarily require a jump host.

Privileged Access and Administrative Security

PCP distinguishes business application access from infrastructure administration. A consultant authorized to view client contacts or update an engagement cannot administer Entra ID, cloud subscriptions, servers, backups, or application hosting by virtue of that business role. Administrative privileges require separate scoped assignments and independent authorization at the target resource.

Trusted administration endpoints

Provide a dedicated, hardened and managed PAW for sensitive administrative work. Separate administrator accounts from routine email and collaboration identities; restrict PAWs to approved management tasks and use strong device compliance policies.

Time-bound elevation

Make sensitive cloud roles PIM-eligible rather than permanently active. Require a task justification, an appropriately short activation duration, and approval for high-impact roles. PIM activation does not replace resource-level RBAC, OS permissions, or separate database access controls.

Management-plane versus server access

Use authorized cloud management interfaces for SaaS/PaaS and Azure resource administration. Where private Azure VMs require interactive RDP or SSH, consider Azure Bastion as a brokered connection path without public VM management ports. Bastion is not itself the source of administrative authority.

Accountability and emergency recovery

Record sign-ins, privilege activations, access approvals and relevant target-system changes. Review privileged access periodically; use separately protected and monitored emergency access accounts with documented recovery tests.

Implementation and verification sequence

  1. Identity and device baseline: Define admin roles and scope, establish distinct administrative identities, require phishing-resistant MFA where feasible, and provision compliant PAWs.
  2. Privilege governance: Configure PIM eligibility, time limits, activation approval for high-impact operations, and resource-scoped RBAC. Confirm selected licensing supports required features.
  3. Controlled access paths: Enforce Conditional Access and target authorization; configure private network policies and deploy Bastion only if private Azure VM administration is in scope.
  4. Logging and emergency operations: Collect administrative audit events, establish alert ownership and recovery accounts, and document incident escalation and credential reset procedures.
  5. Validation and handoff: Test permitted and denied access, elevation expiry, non-privileged user separation, privileged logging, and emergency recovery before production cutover.

Deployment distinction

The current employee workspace demonstration uses client-side role switching, sample records, and local browser storage. It does not use Entra ID, Conditional Access, a protected backend, server-side authorization, or private networking. Those production capabilities would require a separately scoped implementation and security validation.
